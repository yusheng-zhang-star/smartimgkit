GIF 为什么天生就大

GIF 是 1987 年的格式，每帧最多 256 种颜色，而且帧与帧之间没有运动补偿——它只会记录“这一帧和上一帧哪些像素变了”，遇到摄影类画面（渐变、噪点、光影过渡）几乎每个像素都在变，等于每帧都在存整幅图。

所以一段 5 秒、480p 的实拍 GIF 很容易到 5–15MB，而同样内容的 MP4 通常只有它的十分之一。这不是压缩工具不行，是格式本身的效率上限。

压缩 GIF 只有两条路：减少像素（降分辨率）或减少帧（降帧率）。颜色数也能降，但 GIF 本来就只有 256 色，再降会出现明显色带，观感崩得比前两者快。

压缩时该牺牲分辨率还是帧率

优先降分辨率。人对“画面糊”的容忍度远高于“动作卡”，而且 GIF 大多在手机上看，屏幕本身就小，从 800px 降到 480px 肉眼差别有限，体积却掉一半以上。

帧率要谨慎降。30fps 降到 15fps 体积能省近一半，但快速动作（甩头、挥手、镜头平移）会明显一顿一顿。表情包、慢动作演示降到 12–15fps 通常可以接受；游戏录屏、舞蹈视频建议守住 20fps 以上。

如果压到 15fps、480px 还是超过目标体积，说明选错格式了。微信、主流浏览器、大部分社交平台现在都支持 WebP 动图甚至直接发视频，同样观感下 WebP 动图体积通常只有 GIF 的三到五成。GIF 的意义主要在于兼容性，不是效率。

GIF 的透明是单色透明（一个像素要么全透明要么全不透明），重新编码后透明区域会保留，但边缘可能出现一圈锯齿或杂边。需要平滑的透明效果，应该用带 alpha 通道的 WebP 或 PNG 序列。
GIF 的循环次数写在文件头里。重新编码时如果没显式写入，播放器会按默认无限循环处理，观感和原来基本一致。
多半是原始尺寸和时长都太大。GIF 的体积大致正比于“分辨率 × 帧数”，5 秒 30fps 就是 150 帧。这种情况继续压 GIF 收益有限，换成 WebP 动图或直接发 MP4 更实际。
