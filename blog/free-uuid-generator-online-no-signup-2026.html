Common developer use cases for UUIDs

  • Database primary keys for distributed applications — unlike auto-increment integers, UUIDs can be generated on any client without coordination, so no two writes collide even across 1000 servers
  • Session IDs and password reset tokens in web apps — they're unguessable, so attackers can't brute-force other users' sessions
  • File names for uploaded user content — using a UUID as the file name means two users uploading "vacation.jpg" never overwrite each other's files on your server
  • Message IDs in event streaming and message queue systems like Kafka or RabbitMQ — you need globally unique IDs to track events across partitions
  • OAuth 2.0 state parameters and CSRF tokens — they're random, unguessable, and unique per request, which stops cross-site request forgery attacks
  • Testing and development — when you need dummy unique IDs for unit tests, seed data, or demo applications, a UUID generator is the fastest way to make realistic-looking data

What does a UUID actually look like?

A standard UUID v4 looks like this: 3fa2b8e1-1b3d-4e5f-8a9b-0c1d2e3f4a5b. It's 36 characters long: 32 hexadecimal digits separated by 4 hyphens, in the format 8-4-4-4-12. The "v4" means it's entirely randomly generated — there's no embedded timestamp or MAC address, which makes it the most private and secure UUID version. Other UUID versions (v1, v3, v5) embed timestamps or user IDs, which can leak information about when the ID was created and what machine created it. That's why almost all modern applications use v4 UUIDs.

People often ask how many possible UUIDs exist. The number is 2^128, which is about 3.4 × 10^38. To put that in perspective: if you generated 1 billion UUIDs every second for 100 years, you'd still have less than a 0.0000001% chance of ever generating a duplicate. That's why UUIDs are safe to use as primary keys in massive global applications — collision is practically impossible.

New developers often ask why they can't just use auto-incrementing integers as primary keys, instead of going out of their way to generate UUIDs. The main issue with auto-increment integers is that they leak information about how big your application is: if your order IDs are 1, 2, 3... a competitor can just keep incrementing the number and look at your order page to see how many sales you've made, how fast you're growing, and even scrape your entire order history by changing one number in the URL. UUIDs don't have that problem: there's no sequence to guess, no way to tell how many records exist just by looking at one ID, and no easy way to walk through every record in your database by modifying the URL. That's why almost every modern SaaS application — from Slack to Notion to Shopify — uses UUIDs for public-facing resource IDs. It's not just a distributed systems concern; it's a basic security and privacy feature for your users. Even for small side projects, using UUIDs from the start saves you a massive migration headache later when your app grows and you realize you can't expose sequential IDs to the public without leaking sensitive information.
