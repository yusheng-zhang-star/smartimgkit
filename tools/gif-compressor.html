GIF Size Checker

This page reports how large an animated GIF is and hands the same file back to you, entirely inside the browser. It does not re-encode, downscale or drop frames: the download is byte-for-byte what you loaded. That is worth saying plainly, because a browser has no built-in GIF encoder — genuinely recompressing an animation in the page needs a WebAssembly build of ffmpeg or a JavaScript GIF library, and neither ships here. What you do get is a fast size check, and an honest guide to the changes that actually take weight off a GIF.

Why a browser cannot simply recompress a GIF

Canvas can encode exactly three formats: PNG, JPEG and WebP. GIF is not among them, and there is no browser API that takes decoded frames and writes a GIF back out. Doing it in the page therefore means shipping an encoder, and the two realistic options are heavy in different ways. A WebAssembly build of ffmpeg is around 30 MB, needs cross-origin isolation headers to run its threaded version, and takes seconds to boot even on a fast laptop. A JavaScript GIF encoder is smaller but must re-quantise every frame in a worker, and the output quality depends on how well its palette reduction behaves on your particular artwork.

This page ships neither. Rather than fake the work — for instance by handing back the original file and calling it compressed — it measures the file and tells you what to change. If a real in-browser encoder is added later, this description will be replaced at the same time; a page that claims a feature it does not have is worse than one that admits the gap.

Where the weight of a GIF actually comes from

A GIF is a sequence of images, each with its own colour table of at most 256 entries, optionally storing only the rectangle that changed since the previous frame. That structure explains the size behaviour that surprises people:

  • Frame count dominates. Doubling the duration doubles the frames and roughly doubles the file, even if nothing in the scene moves. A ten-second loop at 30 fps is 300 frames; the same loop at 12 fps is 120.
  • Area multiplies quickly. Halving the width and height cuts the pixel count to a quarter, and the saving follows closely because every frame carries that area.
  • Dithering is expensive. Smooth gradients forced into 256 colours get dithered, and dither noise is nearly incompressible — a photographic GIF can be several times larger than a flat-colour cartoon of the same dimensions.
  • Full-frame updates waste space. Many editors export every frame in full rather than only the changed region, which inflates a mostly-static clip several times over.

A quick diagnostic: a GIF that is heavy but visually simple is usually storing full frames or too many of them; a GIF that is heavy and visually busy is usually fighting the 256-colour limit and would be better as video or WebP.

The order that saves the most for the least damage

Work down this list and stop as soon as the file is small enough, because each step costs quality:

  • Cut the duration first. Trim the lead-in, the hold at the end, and any stretch where nothing moves. This is free quality-wise and often the single biggest win.
  • Drop the frame rate, not the size. Most messaging apps and social feeds are watched on a phone at arm's length; 12–15 fps reads as smooth for a short loop, and the saving is proportional to the frames removed.
  • Then shrink the canvas. Match the display size you actually need — a 480-pixel-wide GIF shown in a chat bubble never needs to be 1080 wide.
  • Reduce colours last. Cutting 256 down to 64 or 32 helps, but it is the step most likely to introduce visible banding, so do it after the cheap wins.
  • Consider a different container. For anything longer than a few seconds, MP4 or WebM is an order of magnitude smaller; for short transparent loops, WebP or APNG usually beats GIF on both size and colour depth.

Each of those edits needs an editor that decodes and re-encodes — a desktop tool, an ffmpeg command line, or a dedicated GIF editor. Use this page to establish the baseline size and to decide which lever to pull, then make the change where the encoder actually lives.
